# Open-source trading engine audit

**Checked:** 2026-10-30 UTC. This is a source and public-metadata review of the requested engines, exchange SDKs, AI/research tools, and charting library. I checked GitHub release pages/feeds, release-tag READMEs and licenses, current-branch commit feeds, project documentation, CI/workflow metadata, and security-policy/advisory pages. I did not clone, install, build, run tests, connect to any exchange, or exercise an order or account API. CI links show what the projects configure; they do not mean their checks passed in this review.

## Scope and recommendation

The repository’s current [security requirements](SECURITY.md) keep this dashboard public-data-only: no account access, credentials, private endpoints, order transport, or PAPER feature. The user's manually maintained Bybit positions must remain external and unmanaged. PAPER is described as a separately approved future phase. **No execution engine should be integrated or enabled in the current dashboard slice.** The comparison below is design input only.

**NautilusTrader is the single selected future execution/backtesting engine** for the unified multi-venue event-driven product. Its current Python 3.12-compatible candidate is v1.231.0; GitHub marks that release non-prerelease but titles it “Beta.” Qualify the exact wheel, matching v1 API, adapter behavior, and LGPL-3.0 terms before Phase 3. Do not install or integrate it into the public-data dashboard. Do not mix v2 prerelease examples into v1 code.

Hummingbot's documented no-key `binance_paper_trade` example is a valid lower-friction one-venue alternative if product scope changes. It is not the selected core. Freqtrade is a per-instance directional bot, hftbacktest specializes in HFT replay, and vectorbt is research/backtest tooling; none is a second engine for the selected role.

For Phase 2, use narrow **HTTPX public-read adapters**, not the broad CCXT private/order surface. CCXT's MIT core remains a later breadth option; its Pro WebSocket offering has separate terms. See [exchange capabilities](EXCHANGE_CAPABILITIES.md) for SDK/API evidence and the [architecture](ARCHITECTURE.md) for implementation boundaries.

Current work is Phase 1 research/docs and Phase 2 public dashboard. Phase 3 PAPER, Phase 4 backtesting, Phase 5 AI, Phase 6 Demo, Phase 7 approval workflow, Phase 8 AUTO, Phase 9 QA/security expansion, and Phase 10 live readiness are future work; these documents enable none of them. The [design](superpowers/specs/2026-10-31-multi-exchange-trader-design.md), [plan](superpowers/plans/2026-10-31-public-market-dashboard.md), [AI design](AI_DESIGN.md), [security](SECURITY.md), [QA plan](QA_PLAN.md), and [work log](WORK_LOG.md) define the associated gates.

## Fit rubric

These are this audit’s qualitative fit scores, **not external ratings or claims of product quality**. The score is tied to the documented fit for the stated requirement; no weighted total is calculated.

| Score | Meaning |
|---:|---|
| 0 | No documented support for the capability. |
| 1 | Adjacent research/simulation capability only. |
| 2 | Narrow support, or substantial external/native-language work is needed. |
| 3 | Usable documented support with a material scope or simulation constraint. |
| 4 | Strong documented fit with a meaningful setup, coverage, or maturity caveat. |
| 5 | Direct, first-party documentation matches the capability across the intended workflow. |

Each score in a row is supported by that project's linked findings below: Python-first means documented Python strategy/control APIs on the target runtime; multi-exchange means a single application's simultaneous venue model; order/position lifecycle means documented event/state/accounting depth; replay means historical simulation and execution-model detail. A score of 0 means no support identified in reviewed sources, not proof of impossibility. These ordinal fit scores are not benchmarks. The selected core prioritizes unified venue state and shared event-driven replay over a one-venue quickstart; no arithmetic total is used.

“PAPER/public data” measures documented local simulation while consuming public market data, not proof that a project is structurally incapable of live trading. “Backtest” measures data/execution-model depth, not profitability or predictive validity.

## Project findings

### NautilusTrader

- **Release and maintenance:** GitHub’s latest non-prerelease route resolves to [`v1.231.0`](https://github.com/nautechsystems/nautilus_trader/releases/tag/v1.231.0), dated 2026-08-02. The release title itself says “Beta”; newer [`v2.0.0rc8`](https://github.com/nautechsystems/nautilus_trader/releases/tag/v2.0.0rc8) is a prerelease dated 2026-10-28. The active `develop` branch had a commit on 2026-10-30 ([commit](https://github.com/nautechsystems/nautilus_trader/commit/6dc35da8be6582c9ea71a21e5f6d19f7e9164533)). The [current README](https://github.com/nautechsystems/nautilus_trader/blob/develop/README.md) calls the v1 wheel “stable” while describing the different v2 documentation/API; v1 receives only critical security backports during the transition. That wording does not remove the v1.231.0 release title’s Beta qualification. Pin source, wheel, and matching docs together.
- **License and runtime:** [LGPL-3.0-only](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/LICENSE). It is not a permissive Apache/MIT license; review modification, linking, and distribution obligations for the intended product. Python is first-class for strategy/control code over a Rust engine. The v1.231.0 candidate package metadata requires Python 3.12–3.14; prebuilt wheels mean no Rust toolchain is required for a normal install. Optional Redis persistence adds a service. [README/runtime details](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/README.md), [manifest](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/python/pyproject.toml).
- **Markets and venues:** The project describes CEX/DEX crypto, FX, equities, futures, options, and betting. The v1.231.0 tag’s adapter table includes Binance, BitMEX, Bybit, Coinbase, Deribit, Hyperliquid, OKX, Interactive Brokers, Betfair, and data providers; adapter coverage and stability are venue-specific. The table marks some individual adapters stable, not every product at each venue. [Integrations](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/README.md#integrations).
- **Orders, positions, and WebSocket:** The README documents time-in-force, conditional and advanced order types, post-only/reduce-only instructions, and contingency orders. The engine supports multi-venue routing and NETTING/HEDGING position models. Modular adapters can consume REST APIs or WebSocket feeds. [Position accounting](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/docs/concepts/positions.md), [live/backtest behavior](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/docs/concepts/live.md).
- **Backtest and execution caveats:** Backtests can use historical quote ticks, trade ticks, bars, order books, and custom data at nanosecond resolution across multiple venues. The project distinguishes simulation from live behavior: venue rules, transport/timing, persistence, external activity, and reconciliation can make live results differ. A [sandbox/paper execution client](https://github.com/nautechsystems/nautilus_trader/tree/v1.231.0/nautilus_trader/adapters/sandbox) exists, but the checked documents do not provide a single turnkey, no-key, multi-exchange paper quickstart comparable to Hummingbot’s Binance example. [README features](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/README.md#features), [live differences](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/docs/concepts/live.md).
- **Tests, docs, security, and operational burden:** The repository has a [testing guide](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/docs/developer_guide/testing.md) and build, test, nightly-test, CodeQL, and security-audit [workflows](https://github.com/nautechsystems/nautilus_trader/tree/develop/.github/workflows). Its [security policy](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/SECURITY.md) documents dependency scanning, release provenance, and artifact verification; it also lists upstream `urllib3` advisories addressed in v1.227.0, which is a dependency-remediation record, not evidence of a NautilusTrader vulnerability. The system is aimed at single-node individual/small-team use; it does not include a built-in dashboard or distributed orchestration. Operational burden is medium/high relative to the Python bots because adapter configuration, the Rust-backed event model, venue-specific behavior, and version matching require more engineering, despite prebuilt wheels.
- **Evidence:** [official repository](https://github.com/nautechsystems/nautilus_trader) · [release](https://github.com/nautechsystems/nautilus_trader/releases/tag/v1.231.0) · [license](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/LICENSE) · [docs](https://nautilustrader.io/docs/) · [CI](https://github.com/nautechsystems/nautilus_trader/actions) · [security policy](https://github.com/nautechsystems/nautilus_trader/blob/v1.231.0/SECURITY.md).

### Freqtrade

- **Release and maintenance:** Latest release [`2026.10`](https://github.com/freqtrade/freqtrade/releases/tag/2026.10), dated 2026-10-30. The `develop` branch also had a commit on 2026-10-30 ([commit](https://github.com/freqtrade/freqtrade/commit/7fea5ea24b3c3193cfdd4143b243f7baab66d661)).
- **License and runtime:** [GPL-3.0](https://github.com/freqtrade/freqtrade/blob/2026.10/LICENSE), with copyleft obligations when distributing covered derivative works; get a project-specific license review before embedding it in a separately licensed product. The bot is Python-based and the release manifest requires Python 3.12+. It uses SQLite persistence and provides Docker installation; optional web UI/Telegram controls add services and exposed control surfaces. [README](https://github.com/freqtrade/freqtrade/blob/2026.10/README.md), [manifest](https://github.com/freqtrade/freqtrade/blob/2026.10/pyproject.toml).
- **Markets and venues:** The supported list names crypto spot venues including Binance, Bybit, Kraken, OKX, Gate, and Hyperliquid, plus futures support for Binance, Bitget, Bybit, Gate, Hyperliquid, Kraken Futures, and OKX. Spot is the default; futures/perpetuals and short trades are supported, while the leverage documentation says margin mode is currently unavailable. Exchange and trading-mode behavior varies by connector. It is a bot configured around one exchange per instance, rather than a unified simultaneous multi-venue OMS ([exchange config](https://github.com/freqtrade/freqtrade/blob/2026.10/docs/configuration.md#exchange)). [Supported exchanges](https://github.com/freqtrade/freqtrade/blob/2026.10/README.md#supported-exchange-marketplaces), [leverage/futures notes](https://www.freqtrade.io/en/stable/leverage/).
- **Orders, positions, and WebSocket:** Bot-managed trades support market/limit orders, exchange-side stop-loss where available, and strategy callbacks for additional position adjustments. Futures support leverage/shorting subject to connector rules. The `2026.10` release specifically adds **order-book WebSocket support**; that release note does not establish that all candle, order, or account paths are WebSocket-native. [Strategy/bot loop](https://github.com/freqtrade/freqtrade/blob/2026.10/docs/bot-basics.md), [exchange-specific behavior](https://www.freqtrade.io/en/stable/exchanges/), [release notes](https://github.com/freqtrade/freqtrade/releases/tag/2026.10).
- **Backtest and execution caveats:** Backtesting uses downloaded historical OHLCV candles. Its own docs say callback cadence differs (usually once per candle in backtests versus roughly every five seconds live), dynamic pairlists can use current rather than historical market conditions, exchange funding/mark history may be missing, and dry-run/backtest do not fully capture cross-position influence. A backtest is therefore useful for strategy iteration, not evidence of fill quality or live parity. The project recommends dry-run before live trading. [Backtest](https://github.com/freqtrade/freqtrade/blob/2026.10/docs/backtesting.md), [data download](https://github.com/freqtrade/freqtrade/blob/2026.10/docs/data-download.md), [leverage caveats](https://www.freqtrade.io/en/stable/leverage/).
- **FreqAI:** The optional [FreqAI module](https://github.com/freqtrade/freqtrade/tree/2026.10/freqtrade/freqai) adds ML model training/prediction and backtesting within Freqtrade, not a separate exchange engine. Its [documentation](https://www.freqtrade.io/en/stable/freqai/) requires additional dependencies, data preparation, and temporal leakage controls; no model efficacy was validated here.
- **Tests, docs, security, and operational burden:** It has a broad docs site, a `tests/` tree, and a [CI workflow](https://github.com/freqtrade/freqtrade/blob/develop/.github/workflows/ci.yml). No `SECURITY.md` was found at the audited release/default branch. The logged-out public advisory page fetch exposed no advisory IDs, so advisory status is **unknown**, not “none.” Operational burden is relatively low for one exchange and one bot (Python/SQLite or Docker); multi-exchange operation means separate instances and config/state management. Its docs warn that exchange clock synchronization matters.
- **Evidence:** [official repository](https://github.com/freqtrade/freqtrade) · [release](https://github.com/freqtrade/freqtrade/releases/tag/2026.10) · [license](https://github.com/freqtrade/freqtrade/blob/2026.10/LICENSE) · [docs](https://www.freqtrade.io/en/stable/) · [CI](https://github.com/freqtrade/freqtrade/actions/workflows/ci.yml) · [security advisories](https://github.com/freqtrade/freqtrade/security/advisories?state=published).

### Hummingbot

- **Release and maintenance:** Latest release [`v2.17.0`](https://github.com/hummingbot/hummingbot/releases/tag/v2.17.0), dated 2026-09-22. The `master` branch’s latest commit was also 2026-09-22 ([commit](https://github.com/hummingbot/hummingbot/commit/9af100d6822da7d2d0291a906c730ef172284ee2)); this is an active recent release signal, though less recent than the other active branches checked.
- **License and runtime:** [Apache-2.0](https://github.com/hummingbot/hummingbot/blob/v2.17.0/LICENSE), generally more permissive for integration than the GPL projects, subject to its notice and patent terms. Python strategy scripts sit on Cython-compiled core code; setup requires Python 3.10.12+ and Cython/native compilation. The CLI uses Conda or Docker in the documented paths. [README](https://github.com/hummingbot/hummingbot/blob/v2.17.0/README.md), [setup metadata](https://github.com/hummingbot/hummingbot/blob/v2.17.0/setup.py).
- **Markets and venues:** Connectors cover CEX central-limit-order books (spot and perpetuals), DEX central-limit-order books (spot/perpetuals), and AMM/CLMM/router DEXs. Examples in the current connector table include Binance, Bybit, Coinbase, Kraken, OKX, Hyperliquid, dYdX, Uniswap, and Jupiter. DEX/AMM support can require a wallet or the separate TypeScript Gateway service; connector maturity and product coverage vary. [Connector table and strategy overview](https://github.com/hummingbot/hummingbot/blob/v2.17.0/README.md#exchange-connectors).
- **Orders, positions, and WebSocket:** Connectors normalize REST and WebSocket interfaces. Strategy V2 executors manage order lifecycles for positions, DCA, grids, arbitrage, cross-exchange market making, TWAP, and liquidity provision. The README also lists legacy cross-exchange market making. This is broad exchange-bot execution, not a venue-neutral OMS with the same semantics on every adapter. [Strategies/executors](https://github.com/hummingbot/hummingbot/blob/v2.17.0/README.md#strategies).
- **Paper and backtest caveats:** The README’s `simple_pmm` paper example uses `binance_paper_trade` against live Binance market data and explicitly says no API key is required. It also says **one bot per install**. This gives the clearest no-key public-data simulation path in the set, but the audit did not validate multi-venue paper fills or connector parity. Controllers are described as backtestable, deployable, and tunable live; the README does not establish a common historical order-book replay model comparable to NautilusTrader or hftbacktest. Check per-connector paper fill assumptions before relying on its simulated results. [Paper and live setup](https://github.com/hummingbot/hummingbot/blob/v2.17.0/README.md#hbot-cli), [Gateway and operations](https://github.com/hummingbot/hummingbot/blob/v2.17.0/README.md#docker).
- **Tests, docs, security, and operational burden:** The repo has a `test/` tree and [GitHub workflow](https://github.com/hummingbot/hummingbot/blob/master/.github/workflows/workflow.yml); the docs are maintained in the separate [Hummingbot site repository](https://github.com/hummingbot/hummingbot-site). Its README says live API keys are encrypted in a keystore; the paper example needs none. No `SECURITY.md` was found at the audited release/default branch, and the logged-out advisory page exposed no published IDs; advisory status is **unknown**. Operational burden is medium: Cython compilation, a bot process per install, exchange-specific config, and Gateway if using AMM DEXs. The README explicitly identifies Gateway’s default development HTTP mode as unencrypted and documents a production HTTPS setup; do not use the development mode outside local development.
- **Evidence:** [official repository](https://github.com/hummingbot/hummingbot) · [release](https://github.com/hummingbot/hummingbot/releases/tag/v2.17.0) · [license](https://github.com/hummingbot/hummingbot/blob/v2.17.0/LICENSE) · [docs](https://hummingbot.org/) · [CI](https://github.com/hummingbot/hummingbot/actions) · [security advisories](https://github.com/hummingbot/hummingbot/security/advisories?state=published).

### hftbacktest

- **Release and maintenance:** Latest release is titled `rust-v0.9.4 & py-v2.4.4`, published 2025-12-10 ([release](https://github.com/nkaz001/hftbacktest/releases/tag/rust-v0.9.4)). The latest `master` commit found was 2025-12-23 ([commit](https://github.com/nkaz001/hftbacktest/commit/5f3ec40b2afb764e0fea112f941ed85523ef4e88)). This is an older release/commit signal as of this review, not proof the project is abandoned.
- **License and runtime:** [MIT](https://github.com/nkaz001/hftbacktest/blob/rust-v0.9.4/LICENSE). The backtest API is Python 3.11+ with Numba/JIT and Rust components; the README says live bot deployment is currently **Rust-only**. [README](https://github.com/nkaz001/hftbacktest/blob/rust-v0.9.4/README.rst).
- **Markets and venue scope:** Primarily a high-frequency market-making research/backtest tool. The README supports multi-asset/multi-exchange backtests, with live trading currently listed for Binance Futures and Bybit. This is not broad multi-exchange spot trading support; the README does not enumerate a large stable adapter matrix.
- **Orders, positions, and WebSocket:** The simulation API exposes order submission/cancellation, positions, queue position and fills; examples use limit orders. The project documents historical order-book/trade feed replay and live connectors, but the reviewed README does not establish a general Python live adapter or WebSocket contract. Treat the Python WebSocket/live story as unknown.
- **Backtest and execution caveats:** Strongest specialty here for HFT simulation: full Level-2 Market-by-Price and Level-3 Market-by-Order reconstruction, tick-by-tick replay, feed/order latency models, and configurable queue/fill models. The docs explicitly assume **no market impact** and require sufficiently small orders; they recommend collecting and calibrating real latency and queue behavior because historical replay cannot change the market. Historical depth data must be collected/converted/validated before use. [Data requirements](https://hftbacktest.readthedocs.io/en/latest/data.html), [order-fill assumptions](https://hftbacktest.readthedocs.io/en/latest/order_fill.html), [latency models](https://hftbacktest.readthedocs.io/en/latest/latency_models.html), [live/backtest discrepancies](https://hftbacktest.readthedocs.io/en/latest/debugging_backtesting_and_live_discrepancies.html).
- **Tests, docs, security, and operational burden:** Detailed Read the Docs site and examples are available. Current workflows expose CodeQL, Python release, and stale-bot workflows; no dedicated test workflow was visible in the current `.github/workflows` listing, so automated test coverage/status was not established here. [Workflows](https://github.com/nkaz001/hftbacktest/tree/master/.github/workflows). No `SECURITY.md` was found at the audited branch; the logged-out advisory page exposed no IDs, so advisory status is unknown. Operational burden is high for accurate use: obtain deep tick/order-book data, normalize it, calibrate latency and queue assumptions, and use Rust for the documented live adapters.
- **Evidence:** [official repository](https://github.com/nkaz001/hftbacktest) · [release](https://github.com/nkaz001/hftbacktest/releases/tag/rust-v0.9.4) · [license](https://github.com/nkaz001/hftbacktest/blob/rust-v0.9.4/LICENSE) · [docs](https://hftbacktest.readthedocs.io/en/latest/) · [CI/workflows](https://github.com/nkaz001/hftbacktest/tree/master/.github/workflows) · [security advisories](https://github.com/nkaz001/hftbacktest/security/advisories?state=published).

### vectorbt

- **Release and maintenance:** Latest release [`v1.2.0`](https://github.com/polakowo/vectorbt/releases/tag/v1.2.0), dated 2026-10-19. The `master` branch had a commit on 2026-10-28 ([commit](https://github.com/polakowo/vectorbt/commit/70da8fe7c2a57948ca065ac362fc416bcf31458c)).
- **License and runtime:** Fair-code [Apache-2.0 with Commons Clause](https://github.com/polakowo/vectorbt/blob/v1.2.0/LICENSE.md), not plain Apache-2.0. The clause restricts selling the software; commercial embedding/SaaS use needs careful terms review or a separate permission. Python 3.11–3.14, NumPy/Pandas/Numba, with optional Rust acceleration. [README](https://github.com/polakowo/vectorbt/blob/v1.2.0/README.md), [manifest](https://github.com/polakowo/vectorbt/blob/v1.2.0/pyproject.toml).
- **Markets and execution:** A Python market-data research, indicator, portfolio-analysis, and backtesting toolkit. It does not document native exchange order submission or a live connector layer, and it should not be treated as an execution engine. Its portfolio simulation accepts data and strategy/order logic; there is no native venue-specific spot/perpetual account or order lifecycle. The README’s explicit leverage/contract-multiplier examples link to vectorbt Pro documentation, so do not infer that the open-source package models derivatives venue semantics. No built-in WebSocket connector was identified.
- **Backtest caveats:** Strong for vectorized exploration across many configurations and portfolio analysis, but its focus is not event-level exchange replay, queue modeling, venue latency, or live fill emulation. Execution behavior and source data assumptions need to be supplied and validated by the calling code. It can complement research, not replace the paper/live engine requested here. [Feature overview](https://vectorbt.dev/getting-started/features/).
- **Tests, docs, security, and operational burden:** The repository includes a `tests/` tree, a [tests workflow](https://github.com/polakowo/vectorbt/blob/master/.github/workflows/tests.yml), and an extensive documentation site. No `SECURITY.md` was found at the audited branch; the logged-out advisory page exposed no published IDs, so advisory status is unknown. Operational burden is low as an offline research library, but market-data ingestion and all live/PAPER execution would need to be built separately; the Commons Clause is a significant product-integration consideration.
- **Evidence:** [official repository](https://github.com/polakowo/vectorbt) · [release](https://github.com/polakowo/vectorbt/releases/tag/v1.2.0) · [license](https://github.com/polakowo/vectorbt/blob/v1.2.0/LICENSE.md) · [docs](https://vectorbt.dev/) · [CI](https://github.com/polakowo/vectorbt/actions/workflows/tests.yml) · [security advisories](https://github.com/polakowo/vectorbt/security/advisories?state=published).
