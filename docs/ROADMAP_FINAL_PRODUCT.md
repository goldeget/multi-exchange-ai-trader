### 4.1 선물(USDT linear) 위험 통제 요구사항

모든 값의 **변경 권한은 사용자만** 가집니다. 임계값은 느슨하게 설정할 수 있지만 **명시적으로 입력**해야 하며, 숨은 기본값이 조용히 적용되지 않습니다. AI 출력, 외부 텍스트, 브라우저 요청 본문은 한도를 바꿀 수 없습니다. 아래는 구현 요구사항이며 현재 구현된 것이 아닙니다 (현재 `research/automation.py`의 가상 레버리지 10은 합성 PAPER 전용 값).

| 항목 | 요구사항 |
|---|---|
| 레버리지 범위 (D5) | 거래소가 **종목별로 허용하는 범위를 그대로** 지원. 최소/최대는 런타임에 거래소 instrument·risk-limit 조회로 읽고(위험 한도 구간에 따라 허용 레버리지가 달라질 수 있으므로 포지션 크기 구간별로 재확인), 하드코딩 숫자와 프로그램 자체의 더 낮은 상한은 없음. 조회 실패·데이터 오래됨이면 주문 거절(추정값으로 진행 금지). 거래소가 허용하지 않는 값은 코드에서 거절 |
| 레버리지 선택 | **사용자만** 정함 (설정 화면/명시 입력, 계정·전략별). 숨은 기본값 없음 — 미설정이면 선물 주문 불가. UI가 보수적 값을 미리 채울 수는 있으나 사용자 확인 후에만 저장. AI 출력·외부 텍스트·API 요청 본문으로 변경 불가. 변경은 감사 기록에 남김 |
| 거래당 최대 손실 | **사용자 설정 필수** (금액 또는 계좌 대비 %). 느슨하게 설정할 수는 있으나 반드시 명시적으로 입력해야 함(빈 값/미설정이면 주문 불가). 주문 직전 결정적 코드가 예상 손실(SL 기준, 수수료·funding 포함)을 계산해 초과 시 거절 |
| 청산 거리 vs 손절 | 청산가는 거래소 데이터와 계산식으로 산출(거래소 값과 불일치 시 표시). **SL이 청산가보다 먼저 닿는지 점검**. 허용 여유(예: SL 도달 후 청산까지 남는 %)의 임계값은 **사용자가 명시 설정**(느슨해도 됨). 점검 실패 시 기본 동작은 거절이며, 사용자가 해당 경고를 명시 확인하는 우회 경로를 둘지는 Phase 3에서 사용자와 결정 |
| 경고 표시 (UI/승인 카드) | 모든 선물 추천·승인 카드에 **청산가**, **청산까지 가격 변동 %**, 선택 레버리지, 사용 증거금, SL까지 %, 예상 손실(금액·계좌 대비 %), funding 예상을 눈에 띄게 표시. 갭/슬리피지로 SL이 보장되지 않고 고레버리지일수록 작은 변동으로 청산될 수 있다는 문구 포함. 이 숫자는 코드가 산출하며 AI 텍스트에서 가져오지 않음 |
| 마진 모드 | 격리(isolated) 기본 권장. 교차(cross)는 사용자 명시 설정 시에만. Nautilus `margin_mode` 설정과 실제 계정 상태가 다르면 시작 거부 |
| 포지션 모드 | One-way / Hedge 중 시작 시 **계정 실제 상태를 읽어 일치 확인**, 불일치면 정지. Hedge는 `positionIdx` 처리 필요 (Nautilus 문서). 프로그램이 임의로 바꾸지 않음 |
| 청산 거리 | 주문 전 결정적 코드가 청산가까지 거리(%)와 SL까지 거리를 계산. SL이 청산가보다 가깝지 않으면(안전 여유 미달) 주문 거절. 갭/슬리피지로 SL이 보장되지 않음을 화면에 표시 |
| Funding fee | 진입 전 현재 funding 비율과 다음 정산 시각 표시, 예상 비용을 손익비에 포함. 백테스트에도 반영 (현재 funding 미검증) |
| reduce-only | 청산·익절·손절 주문은 reduce-only 강제. 포지션을 뒤집는 주문 금지 |
| SL/TP | 진입과 함께 보호 주문이 거래소에 걸렸는지 **확인 후에만** 진입 성공으로 간주. 보호 주문 실패 시 즉시 정책대로 처리(신규 차단 + 사용자 알림, 포지션 처리는 사용자 정의 정책) |
| 한도 | 거래당·일일·낙폭 손실, 최대 포지션 수, 총 노출, 연속 손실 정지 (Phase 6 목록과 동일) |

**Nautilus 1.231.0 Bybit Demo 제약 대응** (문서 기준, 직접 실행 검증 전):
- WebSocket 주문 API 미지원 → Demo에서는 어댑터가 HTTP REST로 주문. 지연/속도 제한이 메인넷 경로와 다르므로 Demo 통과가 실거래 지연 특성을 보증하지 않음. `use_ws_execution_fast` 같은 옵션은 Demo에서 쓰지 않음.
- `tp_trigger_price` / `sl_trigger_price` 미지원 (설정하면 주문 거부) → 이 파라미터에 의존하지 않고, 진입 체결 확인 후 **별도 reduce-only 조건부 주문**(예: STOP_MARKET / 지정가 TP)으로 SL/TP를 관리하는 방식을 먼저 시험. 별도 주문 방식이 Demo에서 되는지는 **미검증**.
- Demo 공개 시세는 메인넷 공개 스트림을 쓰므로 가격 데이터 지연/접속 가능 여부도 D1 규칙으로 기록.
- Demo 호가 깊이·체결은 실제와 다를 수 있어 성과 증거로 쓰지 않음.

### 4.2 AI 제공자 인터페이스와 월 예산 상한

- **역할**: AI는 설명 텍스트만 만든다. 위험 한도 변경, 주문, 숫자 결정 권한 없음. 모든 숫자(진입 구간, SL/TP, 수량, 손익비)는 결정적 코드가 산출하고, AI 응답에서 숫자를 읽어 주문에 쓰지 않음.
- **공통 인터페이스**: `provider id / model id / 유료 여부 / 입력·출력 토큰 단가 / 호출 한도`를 선언하는 어댑터. 대상: NVIDIA API, OpenRouter 무료 모델, 유료 Claude Haiku급. 실패·시간초과·형식 오류는 "설명 없음"으로 처리하고 주문 흐름은 영향받지 않음. 조용히 다른 제공자로 바꾸지 않고 표시함.
- **월 지출 상한 (코드로 강제)**:
  - 상한 기본값 100 USD/월, 변경은 사용자 설정 파일/화면에서만 (AI 출력으로 불가).
  - 호출 전: 예상 최대 비용(입력 토큰 추정 + `max_tokens` × 출력 단가)을 계산해 **누적 + 예상 > 상한이면 호출하지 않음**.
  - 호출 후: 제공자가 보고한 실제 사용량으로 누적 기록(원장은 append-only, 월 단위, UTC 기준 월 경계는 구현 시 명시). 사용량 미보고 시 최대값으로 가정해 보수적으로 계상.
  - 상한 도달 시 유료 호출 전체 중지. **자동 충전/구매 없음**. 사용자가 상한을 올리기 전에는 재개하지 않음. 무료 모델은 비용 0으로 계상하되 호출 횟수 한도는 별도 적용.
  - 상한 도달·경고(예: 80%) 시 화면에 표시. 재시작해도 누적은 DB에서 복원(0으로 초기화 금지).
- **키 관리**: API 키는 환경변수 또는 비밀 저장소에서만 읽음. 파일·로그·화면·커밋·프롬프트에 넣지 않으며, 거래소 키·계좌 정보는 AI 요청에 절대 포함하지 않음.
- **무료 모델 한계**: 요청 속도 제한과 응답 품질 편차가 있음. 속도 제한 응답은 재시도 폭주 없이 백오프, 품질은 스키마 검증과 사실 검증(숫자 일치)으로만 통과.
- **확인 필요 (사용 전 반드시 확인)**: 유료 Claude Haiku급의 **정확한 모델명과 토큰 단가는 이번 작업에서 확인하지 못했음** → "to verify before use". NVIDIA API와 OpenRouter 무료 모델의 현재 모델 목록·무료 한도·약관·데이터 보존 정책도 미확인. 단가를 코드에 하드코딩하지 않고 설정값으로 두며, 단가 미설정 시 유료 호출 거부.
- **데이터 전송**: 공개 시세에서 파생된 값만 전송. 개인 포지션/잔고 전송은 별도 사용자 승인 전까지 금지.

## 5. 단계별 계획 (선물 우선으로 조정, 순서 고정)

각 단계는 이전 단계의 완료 기준을 통과해야 시작합니다. 비밀키는 파일·로그·커밋에 넣지 않습니다. 출금 권한 키는 어떤 단계에서도 사용하지 않습니다. 접속 결과는 가능/차단/미검증으로 기록합니다.

### Phase 1. PAPER 안정화 (Linux/WSL)
- 목표: Linux에서 `uv sync --locked`, pytest, ruff, mypy, npm test/build 통과 기준선 확보. WSL 설치 작업 종료 후 진행.
- 완료 기준: CI와 동일한 명령 통과, 기존 DB/work 보존, 재시작 복구 확인.
- 사용자 준비: 없음.

### Phase 2. Bybit 선물(USDT linear) 공개 시세 + 읽기 전용 계정
- 목표: **linear 무기한** 공개 시세(ticker, 캔들, funding, mark price)와 읽기 전용 조회(잔고, 포지션, 주문, 계정의 마진/포지션 모드, 레버리지). spot은 같은 구조로 보조 추가. 주문 함수는 넣지 않음.
- 접속 상태는 가능/차단/미검증으로 기록 (D1). 차단이면 중단하고 보고, 우회 없음.
- 설계 필수: 조회 결과마다 `origin = program | external | unknown`. 기존 수동 포지션은 항상 `external` (D4).
- 완료 기준: 읽기 전용 테스트(권한 없는 호출은 거절), 키 노출 방지 테스트, 시세 신선도/정지 표시.
- 사용자 준비: Bybit 읽기 전용 API 키. **출금·거래·이체 권한 끔**, 가능하면 IP 제한, 환경변수로만 설정. 접속 환경은 사용자가 직접 마련(D1). 시작 전까지는 준비할 것 없음.

### Phase 3. 선물 위험 엔진 (결정적 코드, 주문 없음)
- 목표: 4.1의 계산 모듈 — 레버리지 상한, 마진/포지션 모드 검증, 청산 거리, funding 비용, 수량·증거금·예상 손실(계좌 대비 %) 산출. 단위 테스트와 속성 테스트로 검증. 설정 변경은 사용자 경로로만.
- 완료 기준: 위반 입력은 전부 거절, AI/외부 입력 경로로 설정 변경이 불가능함을 테스트.
- 레버리지 허용 범위는 거래소 데이터에서 런타임 조회(D5). 코드에 상수 없음. 미설정 시 주문 불가 테스트 포함.
- 사용자 준비: 거래당 최대 손실, 청산 여유 임계값을 직접 정함(느슨해도 되지만 명시 필요). 레버리지 값은 사용 시점에 사용자가 직접 선택.

### Phase 4. Bybit Demo 선물 주문 수명주기
- 목표: Demo 키로 주문 생성, 부분 체결, 취소, 응답 유실, 재시작 후 reconcile, **별도 reduce-only SL/TP 주문 관리**를 실제로 시험. 주문 생성 경로는 Nautilus 하나. 4.1의 Demo 제약을 먼저 시험해 결과를 기록.
- 완료 기준: 체결 중복 0, 고아 주문 0, 재시작 후 상태 일치, 보호 주문 실패 시 정책대로 동작.
- 사용자 준비: Bybit Demo 전용 키 (실계좌 키와 별개).

### Phase 5. AI 설명 + 사용자 승인 (모드 A)
- 결정적 신호/위험 계산이 숫자를 만들고 AI는 설명만 (4.2). 추천 필드(거래소, 종목, 선물/현물, 방향, 데이터 신선도, 시간대, 진입 구간, SL/TP, 손익비, 수량/레버리지/증거금, 청산 거리, funding 예상, 예상 손실과 계좌 대비 %, 찬반 근거, 무효 조건) 저장. 만료 시각과 주문 직전 재검증 필수.
- 월 지출 상한 코드, 제공자 인터페이스, 키 환경변수 처리 포함. 유료 모델명·단가는 사용 전 확인.
- 사용자 준비: 사용할 제공자 키(환경변수), 확인된 유료 모델명과 단가, 월 상한 확인.

### Phase 6. 장기 실데이터 전략 검증 (선물 중심)
- 수수료, 슬리피지, **funding**, 시간순 OOS, 공유 자본 포트폴리오, 청산 모델 포함. 손실도 그대로 기록 (현재 BTC/ETH spot OOS는 손실). 통과 기준은 사전에 문서로 확정.
- Bybit 접속이 가능할 때만 실제 선물 데이터 사용, 아니면 BLOCKED로 기록.

### Phase 7. 제한적 자동매매 (모드 B)
- 승인 모드와 **별도 설정**. 허용 거래소/종목/전략, 계좌별 한도, 거래당/일일/낙폭 손실, 최대 레버리지/포지션/노출, 연속 손실 정지, 신호 TTL, 쿨다운, 데이터 지연·연결 실패 정지.
- 정지 의미 3가지 분리 정의·테스트: (a) 신규 진입만 차단 (b) 미체결 주문 취소 (c) 포지션 청산(긴급중지). 기본은 (a), 청산은 명시 행동.
- 이 단계 이전에 **수동 포지션 처리 방침(D4)을 사용자가 결정**. 결정 전에는 external 유지.

### Phase 8. Bybit spot 보조 + Binance / OKX 확장
- spot은 보조 시장으로 추가. 거래소 간 동일 가정 금지(최소 주문, 포지션 모드, 관리 주문, Demo 차이). 거래소마다 Phase 2~4 재통과. OKX는 공식 V5 계약 검증부터.

### Phase 9. 실거래 준비 점검
- 사용자의 **별도 명시적 승인** 없이는 시작하지 않음. 소액 한도, 보안 검토, 복구 절차 포함. 수익을 보장하지 않음.

## 6. 아직 남은 결정/확인

1. 거래당 최대 손실과 청산 여유 임계값 (사용자가 명시 설정, Phase 3 시작 전). 청산 경고 우회 확인 경로를 둘지 여부. (레버리지 값 자체는 D5에 따라 사용자가 사용 시점에 선택)
2. 유료 AI 모델의 정확한 이름·단가, NVIDIA/OpenRouter 무료 모델 한도 (사용 전 확인).
3. 수동 Bybit 포지션 처리 방침 (프로그램 완성 후, D4).
4. Bybit 접속 환경 준비 완료 시점 (사용자 통보 후 접속 테스트, `MARKET_DATA_BLOCKED_HOSTS` 변경 여부도 그때 사용자가 요청).
