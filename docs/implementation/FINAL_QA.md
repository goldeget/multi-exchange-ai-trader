# 최종 통합 검증과 지원 범위

기준 설계는 `docs/UI_ARCHITECTURE.md`, 시각 원본은 `docs/ui-reference/original`의 24장입니다. 원본 ZIP과 개별 이미지의 SHA-256을 확인했고 원본 바이트를 보존했습니다. 이전 채팅 전체나 제공되지 않은 운영 DB를 복구했다는 의미는 아닙니다.

캡처 소스 `e0d6bfa1887ac2025d780e99d8cdc5c1583e1be0`의 [CI 41290522060](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41290522060)은 다섯 작업을 모두 통과했습니다.

## 화면 기준과 검토 방법

엄격 비교 [CI 41279473947](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41279473947)에서는 브라우저 5개가 실패했고 나머지 네 작업은 통과했습니다. 실패를 합격으로 처리하지 않았습니다. 실제 브라우저에서 전역 표 테두리가 차트 내부 표에 적용되어 PC 차트 높이가 5,617px까지 늘고 전체 페이지 캡처마다 증가하는 문제를 확인했습니다. 내부 표 스타일을 격리하고 PC 차트 높이를 490px로 제한했으며, 번들 글꼴 준비 뒤에만 캔버스 차트를 생성하도록 수정했습니다. 반복 전체 페이지 캡처의 높이 불변 검사와 글꼴 대기·해제·실패 검사를 추가했습니다.

후속 검토용 실행에서는 동일 PNG 두 장이 연속으로 정확히 일치한 경우에만 후보를 저장합니다. 최대 8회 안에 안정되지 않으면 실패합니다. 새 후보를 다시 검토해 승인한 뒤 캡처 전용 설정을 제거하고 엄격 비교를 다시 수행합니다. 허용 차이·마스크·이미지 자동 갱신으로 실패를 숨기지 않습니다.

엄격 비교 [CI 41282249161](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41282249161)에서는 320px 시장 캔버스의 가격 점선 한 행에서 원시 RGB 6픽셀 차이가 관찰됐고, Playwright가 그중 1픽셀을 실패로 판정했습니다. 다른 브라우저 95개와 네 작업은 통과했습니다. 같은 실행 안의 후보·실제·실패 캡처는 바이트가 동일해, 단순 대기 부족과 구분했습니다. CPU별 래스터 경로 차이를 점검하기 위해 [Chromium의 웹 테스트용 기본 CPU 경로 옵션](https://chromium.googlesource.com/chromium/src/+/HEAD/content/public/common/content_switches.cc#256) `--disable-skia-runtime-opts` 하나만 브라우저 검사에 추가합니다. 기존 승인 PNG 148개와 오차 0 조건은 그대로 비교하며, 이 가설의 검증 결과는 최종 PR·메인 검사에서 확인합니다. 제품 캔버스의 선·색·글꼴이나 비교 대상은 변경하지 않습니다.

위 단일 옵션을 사용한 [CI 41283054005](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41283054005)도 기존 CPU 경로로 생성된 기준과의 미세 색상 차이로 브라우저 18개가 실패했습니다. 따라서 단일 옵션 추가만으로 기존 기준 비교가 통과했다고 주장하지 않습니다. 검사 환경을 이 기본 CPU 경로로 고정한 상태에서 148개 후보를 새로 생성·검토·명시적으로 승인한 뒤, 별도 PR 실행과 메인 실행에서 다시 오차 0 비교합니다. 원래 원본 24장과 제품 UI 코드는 이 환경 정규화 과정에서 바꾸지 않습니다. 앞선 실패와 이전 승인 해시는 남겨 두며, 자동 기준 갱신이나 허용치 완화로 대체하지 않습니다.

새 기준을 사용한 [CI 41284705121](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41284705121)에서도 같은 320px 시장 차트에서 1픽셀 실패가 재발했습니다(95개 통과, 24개 명시적 제외). CPU 최적화 옵션만으로 캔버스 경로가 안정화됐다는 가설은 입증되지 않았습니다. 다음 검사는 `--disable-accelerated-2d-canvas`도 추가해 2D 캔버스를 소프트웨어 경로로 고정하고, 기존 차트 높이 검사에 Chromium의 실제 GPU 기능 상태·기기·드라이버와 브라우저/CPU 환경을 첨부합니다. 제품 UI·캔들 데이터·비교 허용치는 바꾸지 않으며, 이 환경의 후보 재검토와 별도 엄격 검증을 통과해야 합니다.

- 고정 Linux·Chromium·로컬 Pretendard, 한국어·한국시간·고정 시계·고정 예시를 사용합니다. PC 1440×1024, 모바일 390×844, 추가 폭 320·360px를 확인합니다.
- 총 148개: 정상 화면 48개, 실제 컨트롤러의 오프라인 화면 48개, 좁은 화면 48개, 확인 대화상자 4개입니다. 첫 화면과 전체 페이지를 함께 보존합니다.
- 세 담당자와 통합 담당자가 분담했습니다. 오프라인·좁은 화면·전반부 화면은 별도 담당자가 확인했고, 후반부 화면과 대화상자는 통합 담당자도 직접 확인했습니다. 구현자가 자신의 화면도 검토한 범위는 독립 검토로 과장하지 않습니다.
- 후속 캡처에서 이전 승인 이미지와 대상 경로·SHA-256이 모두 같은 경우에만 승인을 재사용했습니다. 바뀐 이미지는 다시 보았고, GitHub가 반환한 저장값을 로컬 Git blob 값과 대조했습니다.
- `docs/ui-reference/reviewed-baselines.json`은 각 이미지의 출처·크기·SHA-256·Git 저장값을 기록합니다. 승인 이미지 자체도 저장소에 포함합니다.
- 원본 24장에 대한 나란히 보기·50% 겹침·차이 이미지 72개는 별도 증거 묶음에 보존합니다. 생성형 원본과 2 CSS px 이내의 일치나 사진과 같은 완전 일치를 입증한 것은 아닙니다.

필수 장부 선택·저장 설정·서버 검토 조건과 16px 본문·14px 보조 설명·44/48px 조작 영역을 유지하면서 일부 주요 버튼은 세로 스크롤 아래에 배치됩니다. 수치와 단위를 줄바꿈으로 분리하거나 글자를 축소해 원본 한 화면에 맞추지 않습니다. 서로 모순되는 원본 수치, 네이티브 틱과 퍼센트, 실제 지원 여부의 차이는 `visual-exceptions.json`에 기록했습니다.

## 구현한 기능과 실행 조건

| 범위 | 판정 |
|---|---|
| 공통 PC·모바일 화면 | 실제 조회와 예시가 같은 컨트롤러·표현 컴포넌트를 사용. 조회 실패·빈 목록·지원 미확인을 구분 |
| 수동 현물 PAPER V2 | 별도 CASH 장부의 시장가·지정가·예약·취소·수수료·보유 범위 매도. 검토와 확정, 만료·재시작·응답 유실·중복 방지 포함 |
| 자동실행·평가 V2 | 신규 진입 정지와 전체 정지 구분, 저장 레버리지·구성 식별값, 위험 한도, 비용·기간·미사용 구간 검증. 기존 V1 계약 보존 |
| 규칙 추천 | RULE 출처·목록·상세·선택 경합·유효시간·승인 효과 구분. 유료 AI 분석으로 표시하지 않음 |
| 조회·복구 | 독립 장부, 최근 감사 순번, 지연 응답 무시, 재시작 후 명시적 재개, 같은 요청 키로 결과 대조 |
| AI 내부 예산 | OFFLINE_TEST에서 원자적 예약·정산·불확정 비용 보존. 실제 제공자 잔액이나 과금 검증과 별개 |

네이티브 PAPER·자동실행·평가는 검증된 Linux x86_64·Python 3.12·NautilusTrader 1.231.0·네트워크 차단 장치 조건에서 지원합니다. Windows 네이티브 실행은 지원하지 않으며 다른 엔진으로 우회하지 않습니다. 합성 가격·전량 유동성 등 계산 가정은 실제 체결·실제 선물 데이터·수익성 검증이 아닙니다.

실제 AI 제공자·모델·권한·잔액·유료 호출은 미설정 또는 미검증입니다. 실제 계좌의 현재 권한과 잔고도 이번 작업에서 확인하지 않았습니다. Cursor가 메인에 반영한 별도 DEMO 승인 계약은 통합했으며, 이번 검증에서 DEMO 또는 LIVE 주문을 실행하지 않았습니다. DEMO 고정 매수·감축 요청의 접수 응답은 체결·포지션 종료 확인을 의미하지 않습니다.

실제 휴대전화 원격 접속·인증된 HTTPS 진입점·기기 세션은 미구성·미검증입니다. 실제 OS 가상 키보드와 실제 브라우저 200% 확대도 검증하지 않았습니다. 320/360px 반응형 검사를 이들 검사로 바꾸어 부르지 않습니다. 기본 loopback·Host·Origin 보호는 유지합니다.

## 시작·종료·복구

[사용자 안내](USER_HANDOFF_KO.md)에 화면 예시, 검증된 Linux 실행 조건, 종료 전 처리 대조와 백업·복구 방법을 정리했습니다. 원문 키·개인 환경설정·운영 DB는 소스나 화면 증거 묶음에 넣지 않습니다. 미확정 요청을 새 요청으로 바꾸거나 장부를 삭제해서 해결하지 않습니다.

최종 사용자가 검사 후 GitHub 메인 병합을 명시적으로 지시했습니다. 원본 설계 문서에 보존된 이전 자동 병합 금지 문구와 구별하며, 최종 검사·최신 메인·예상 소스 일치를 확인한 후에만 병합합니다. 병합이 계좌·유료 모델·실거래 활성화를 뜻하지 않습니다.

## 병합 후 재촬영 검사 보완

[PR #9](https://github.com/goldeget/multi-exchange-ai-trader/pull/9)의 최종 엄격 [CI 41286300474](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41286300474)는 다섯 작업을 통과했고, 148개 저장 후보의 SHA-256이 승인 이미지와 모두 같았습니다. 병합 후 첫 메인 [CI 41286862478](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41286862478)에서는 PC 현물 주문 검토 대화상자의 추가 전체 페이지 촬영이 9픽셀 차이로 실패했습니다. 원시 RGB 대조에서는 닫기 버튼 아래 둥근 테두리의 13픽셀 차이였고, 같은 실행에서 먼저 저장한 148개 후보는 모두 승인 이미지와 바이트가 같았습니다. 실패를 합격으로 바꾸거나 승인 기준을 갱신하지 않았습니다.

기존 연속 두 장 정확 일치·최대 8회 조건을 만족한 PNG Buffer를 그대로 같은 승인 경로의 이미지와 비교합니다. `toMatchSnapshot`의 `maxDiffPixels=0`, `threshold=0`을 유지하고 SHA-256 정확 일치도 요구합니다. 비교를 위해 페이지를 추가 촬영하지 않으므로 캡처 전용 모드와 엄격 모드의 페이지 촬영 순서가 같습니다. 기준 누락·자동 갱신·스냅샷 검사 생략은 실패합니다. 제품 코드·승인 PNG 148개·렌더러 설정은 변경하지 않습니다. 이 후속 수정의 별도 PR 검사와 새 메인 검사 결과는 외부 완료 보고서에 기록하며, 앞선 실패나 PR #9의 성공으로 대신하지 않습니다.

## 안정 버퍼의 실제 래스터 차이 조사

후속 [PR #10](https://github.com/goldeget/multi-exchange-ai-trader/pull/10)의 [CI 41288034733](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41288034733)는 다섯 작업과 148개 후보의 정확한 해시 비교를 통과했습니다. 그러나 다음 메인 [CI 41288617958](https://github.com/goldeget/multi-exchange-ai-trader/actions/runs/41288617958)에서는 저장 안정 버퍼 자체가 두 화면에서 달랐습니다. 생성된 146개 중 144개가 기준과 같았고, PC 대화상자 닫기 모서리는 원시 5픽셀·최대 채널 차이 1, 320px 시장 가격 점선은 원시 6픽셀·최대 차이 4였습니다. 비교 도구는 각각 3픽셀과 1픽셀 실패로 판정했습니다. 따라서 추가 재촬영 제거만으로 전체 재현성이 해결됐다고 주장하지 않습니다.

후속 제품 수정은 현재가격 라벨과 점선의 의미를 유지하면서 점선을 정수 비트맵 사각형으로 그리고, 대화상자 제목의 줄 상자와 중앙 배치 좌표를 물리 픽셀에 맞추는 것입니다. 모서리·문구·조작 영역을 제거하거나 이미지를 가리지 않습니다. 각 후보에는 캔버스·대화상자의 실제 좌표·DPR·크기를 기록합니다. 변경한 제품의 후보를 명시적으로 재검토한 뒤 별도 엄격 PR 검사와 메인 검사를 다시 통과해야 합니다. 새 결과가 나오기 전에는 이전 캡처나 병합 성공을 최종 합격으로 사용하지 않습니다.
