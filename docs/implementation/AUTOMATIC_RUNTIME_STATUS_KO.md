# 자동 운용 구현 및 미완성 경계

이 변경은 최종 실거래 프로그램의 완성 또는 실계좌 운용 개시를 뜻하지 않는다.

## 구현한 경로

- FULL_AUTO와 ALL_IN_ONE의 기존 서버 후보 검증을 영속 주문 의도·예약·네이티브 주문 전달 코드에 연결했다. ACK와 체결은 구별하고, 통신 불확실성·재시작 시 주문을 자동 재전송하지 않는다.
- 포지션별 상태와 이벤트 저장소를 분리했다. 신규 진입을 일시정지해도 기존 소유 포지션의 읽기 감시 경로는 유지한다.
- 기존 Bybit GET 전용 클라이언트에서 원시 레버리지·TP/SL·청산가를 읽되, 이를 실제 소유권·보호 주문·완전한 청산 증명으로 승격시키지 않는다. 중복 JSON 키·비정상 숫자·응답 크기 초과도 거절한다.
- OpenRouter 생성 호출은 명시적인 서버 호출에서만 가능하며, 최신 모델 가격에 근거한 보수적 비용 예약·영속 단일 호출·실제 요금 정산·불확실 요금 보존을 사용한다. AI는 허용된 후보 ID만 선택한다. 키 등록과 화면의 예산 저장은 호출 권한이 아니다.
- 웹 설정에서 최대 배정 자금·손실·레버리지·종목·전략 등 미정 항목을 남겨 둔 채 부분 저장할 수 있다. 저장은 운용을 시작하지 않는다. 동시 수정은 설정 버전으로 충돌을 검출한다.
- 백업은 기존 여섯 장부와 존재하는 실행 상태·정책·AI 호출 기록을 함께 검증한다. 실제 운용용 전체 파일 집합은 별도 엄격 옵션으로 요구한다.

## 후속 네이티브 제어·이력·작업자 변경

- 동일한 핀 고정 네이티브 클라이언트의 소유 주문 취소와 정수·분수 레버리지 적용을 영속 명령·독립 조회·주문 직전 재검사에 연결했다. 취소·만료 증거의 거래소 주문 신원을 대조하고, 한 주문에 미확정 취소 의도를 중복 생성하지 않는다. 실제 효과 검증 전에는 운용 차단을 해제하지 않는다.
- 인증 GET 세션에서 체결·주문·계좌 전체 거래내역·위험한도를 읽는 계약과 UTC 자정 현금 기준의 수수료·펀딩 포함 실현손익 계산을 추가했다. 조회 페이지 완료는 실제 사건의 완전성 증명이 아니며, 일일 장부의 자격은 계속 미확정이다. 기준 잔액과 모르는 활동은 추정하지 않는다.
- 실제 Linux 네이티브 노드와 단일 계좌 작업자, 명시적인 관찰 전용 CLI 및 비활성 서비스 예시를 추가했다. 기본 CLI는 키·네트워크·DB에 접근하지 않는다. 작업자 관찰을 명시해도 자동 주문이나 유료 AI가 시작되지 않는다.
- 작업자 종료 시 신호 처리 소유권을 유지하고, 소유 체결 이벤트를 네이티브 큐 소진까지 보존한다. 종료를 확인하지 못하면 DB와 계좌 잠금을 유지하며 성공한 종료로 보고하지 않는다.
- 이 작업자의 실행 파일 경로·별도 잠금 경로·백업 경로는 같은 배치 계약을 따른다. 이전 이름의 실행 장부가 있으면 빈 장부로 대체하지 않고 명시적인 복구 검토를 요구한다.

## 영속 이력 및 오프라인 복구 범위

- `history.sqlite3`에 계좌·환경을 고정하고 완료된 조회의 원래 관찰 시각, 체결·주문·거래내역 변형과 충돌을 원자적으로 보존한다. 같은 계좌 거래내역을 여러 종목에서 읽어도 같은 변형은 한 번만 표시한다. 종목이 빈 이체도 보존한다.
- `coverage`와 `load_window`는 명시적인 최대 7일 구간의 겹침·인접 구간, 빈틈, 충돌을 보여 준다. 체결·주문 조회 범위는 종목별이고 거래내역 조회 범위는 계좌 전체다. 나중에 발견한 충돌은 과거 관련 구간에도 표시한다. 주문은 생성 시각으로 조회하며, 정상적인 후속 변경과 실제 갱신 시각 기준의 체결량 역행·동시각 충돌을 구별한다.
- 작업자는 `collect_history(symbol, start_ms=..., end_ms=...)`를 명시적으로 호출할 때만 수집한다. 기존 `read_history`는 읽기 전용이다. 조회 전후 작업자·계좌 잠금 획득 세대·인증 세션·종목·범위를 대조하며, 종료 요청 후 도착한 결과는 저장하지 않는다. 임시 데이터의 실제 백업·복원 시험은 다음 날 새 작업자로 복원해도 원래 시각과 BLOCKED·STOPPED 상태를 유지하는지 확인한다. 실제 거래소·배포 자격과는 별개이며 자동 최초 시작점·조회 주기·시작 플래그는 추가하지 않는다.
- `state_snapshot.py`와 같은 폴더의 `history_snapshot_validation.py`는 애플리케이션 설치 없이 Python 3.12 표준 라이브러리만으로 동작한다. 정지한 원본의 바이트와 WAL을 복사하고 복사본만 SQLite로 검증한다.

| 백업 형식 | 파일 집합과 요구 옵션 |
| --- | --- |
| v1 | 기존 여섯 장부와 datasets |
| v2 | 기본 집합과 존재하는 기존 런타임 파일. `--require-runtime`은 기존 네 파일 전체를 요구 |
| v3 | 기본 집합과 history·execution·runtime-state 세 파일. `--require-history`로 명시적으로 요구 |
| v3 + 두 옵션 | 기존 네 런타임 파일 전체와 history 모두 요구 |

기존 네 런타임 파일은 execution·runtime-state·runtime-policy·ai-dispatch다. 이력 관찰용 백업에는 AI dispatch나 정책 파일이 필수가 아니며, 있으면 함께 보존한다. history가 있으면 옵션 없이도 execution·runtime-state가 반드시 함께 있어야 한다. v3 manifest의 `history_files`는 정확히 `["history.sqlite3"]`이고 `runtime_files`는 존재하는 기존 런타임 파일 목록이다. v1/v2의 이력 포함·주장, 필수 이력 누락, 알 수 없는 파일·잠금 파일은 거절한다. 복구 시 빈 이력을 만들지 않으며 기존 유효 v1/v2와 정책 단독 부분 백업은 계속 읽을 수 있다.

스키마·키·외래 키·CHECK·추가 전용 트리거와 정규 payload·해시·모든 결정적 충돌을 검증한다. 두 짝 저장소의 모든 계좌·환경 행은 history의 단일 scope와 같아야 한다. 빈 저장소에서는 다른 scope를 추론하지 않는다. manifest 해시는 우발적 손상 검출용이며 같은 scope의 독립 파일을 섞고 해시를 다시 만든 경우의 역사적 진위 증명은 아니다.

복구 후에도 관찰 시각을 새로 찍지 않는다. 조회 완료는 거래소 사건이 모두 도착했다는 증거가 아니다. `query_complete`와 충돌 여부는 별개이며 `venue_event_complete`, `flat_verified`, `DailyRealizedLoss.ledger_qualified`는 계속 false다. 런타임 BLOCKED·정책 STOPPED를 유지한다.

이 변경으로도 지연 사건의 완전한 대조, 재시작 후 네이티브 주문 캐시 복구, 계좌 전체 위험·청산 증거, TP/SL 자식 주문의 확인·수리, 실제 전략 신호와 자동 주기 연결은 완료되지 않는다. 실행 진입점은 빈 계획 레지스트리와 고정 차단을 유지한다. 아래 실제 운용 전 목록은 이러한 코드와 실제 DEMO·서버 증거를 모두 충족해야 한다는 의미다.

## 실제 운용 전에 남은 구현·검증

1. 거래소 인증 UID/서브계좌와 네이티브 채널의 일치 검증.
2. 완전한 체결 이력·수수료·펀딩·실현손익 장부 및 확정 청산 후 예약 해제. 엔진 대조 과정의 추정 체결과 실제 거래소 execution 증거를 구별하는 검증도 필요하다.
3. 단일 네이티브 경로의 레버리지 적용, 독립 조회 확인, 주문 직전 재검증.
4. 거래소 부착 TP/SL 자식 주문의 소유권·수량 확인, 취소·복구·교체, 보호 실패 시 안전한 위험 축소.
5. 위 검증을 수행하는 실제 Linux 상주 작업자와 신호·전략 데이터 흐름 연결, 실제 DEMO 체결·익절·손절·재시작 시험.
6. 사용자 운용 금액·위험 한도, AI 지출 한도, 상주 서버 월 비용 확정 및 서버 배포.

이 항목들은 단순히 설정을 켜서 해결되지 않는다. 현재 실행 코드의 고정 검증 차단을 제거하거나 가짜 증거로 대신해서는 안 된다. 모의 테스트의 private gate 대체는 테스트 범위에서만 사용하며 실거래 검증이 아니다. LIVE 준비 상태와 외부 호출 자동화는 계속 비활성이다.

## 운영·비용

이 구현 과정은 실제 주문, 실제 유료 AI 생성, 서버 생성·결제를 수행하지 않는다. 기존 시험 서버의 삭제와 상주 서버 배포는 서로 다른 상태다. PC 종료 후 지속 실행은 상주 서버 배포와 검증이 끝난 이후에만 성립한다. 프로모션 크레딧만으로 영구 무료 또는 카드 청구 차단을 보장하지 않는다.
