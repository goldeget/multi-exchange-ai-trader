# Exchange API capabilities and dashboard scope

Research checked on 2026-10-30 against the linked GitHub repositories and package registries. A capability described by an API or SDK source is not evidence that this application implements or has exercised it. Exchange documentation pages that could not be fetched from this environment are identified as not revalidated.

## Current dashboard boundary

The first dashboard is public-data-only. It does not configure API credentials, create authenticated clients, call private account endpoints, or make exchange order calls. Private account and order capabilities below are research notes only and are **disabled** in this dashboard. Existing manually maintained exchange positions remain outside the application and unmanaged.

Exchange Testnet/Demo environments are exchange endpoints, not local PAPER simulation. They can still involve authenticated account and trading endpoints. Neither Testnet nor Demo account integration is part of this dashboard. A future PAPER simulator, if separately approved, must keep simulated orders and fills inside the application and must not forward them to an exchange.

## Security and operational caveats

- Public responses are untrusted input. Validate schemas, finite decimal values, instrument metadata, timestamps and freshness; preserve the source venue and raw symbol. A stale or incomplete feed must not look current.
- Do not put exchange keys in the browser, repository or logs. If private access is ever separately authorized, use keys with the least required permissions, disable withdrawals, restrict source IPs where available, protect signing secrets, and keep mainnet and Testnet credentials separate.
- SDKs do request signing and transport; they do not provide application-level risk limits or guarantee a safe trade. Review dependencies and release changes before upgrading. Avoid debug logging that may expose signed headers or request data.
- Do not automatically retry an order write after a timeout unless the request has a documented idempotency mechanism and the order state has been reconciled. An unknown response can mean the exchange accepted the operation.
- Apply per-venue rate-limit budgets across the whole deployment, not just one SDK instance. Use bounded retries with backoff for public reads and surface feed gaps or throttling instead of presenting cached data as live.
- Testnet/Demo behavior, market depth, fills and symbol coverage may differ from mainnet. It is neither local PAPER execution nor evidence of a production fill model. No numeric provider rate budgets are asserted here: budgets are endpoint-, product- and account-dependent. Official Binance/Bybit source notes support the narrow read candidates below; OKX official contracts and budgets remain unverified.

## Integration choice for Phase 2

Use **narrow HTTPX public-read adapters** in the first dashboard. Fixed host/route allowlists, local symbol mappings, bounded polling and response normalization keep signing, credentials and order/private methods outside the process. This choice trades broader ready-made normalization for explicit endpoint ownership and a smaller callable surface. No engine is installed for this phase. [NautilusTrader is the single future engine](OPEN_SOURCE_AUDIT.md#scope-and-recommendation), subject to candidate package/API/license qualification before Phase 3.

CCXT's MIT core remains a possible later option if exchange breadth expands. Do not add it to the first dashboard dependency set. CCXT Pro WebSockets have separate terms; review those before any future adoption. Initial transport is REST polling. No project WS capability in this document proves managed-environment WS connectivity.

The official venue SDKs remain research references for future endpoint-specific work. Binance's modular clients require separate module/version maintenance. Bybit's Python SDK has more reviewed history than its new 0.x TS/Rust clients. No first-party general OKX V5 CEX trading SDK or usable license for the unofficial Python wrapper was verified; do not install the wrapper.

## Verification limits

This was a source and release-metadata review, not a runtime integration test. No exchange requests were sent, no credentials were used, and no create/cancel/order/account operation was exercised. OKX's official docs host could not be fetched under the environment's current network allowlist; its V5 page is linked for follow-up, but public ticker/candle method names were only confirmed in the unofficial `python-okx` source (`get_ticker`, `get_tickers`, `get_candlesticks`, `get_orderbook`). Confirm exact current routes, response schemas, limits, Demo behavior and liquidation coverage against the official V5 docs before enabling any OKX adapter. Until then its public reads are disabled as well as all private/order features.
